# 0019. ファイル操作は expo-file-system を直接使い、テストでは node の fs で動く偽物に差し替える

- 状態: 承認
- 日付: 2026-09-28

## 背景
本棚フォルダを正本にすると（ADR 0016）、ノートの作成・名前変更・移動・削除や外部変更の反映など、ロジックの中心がファイル操作になる。v1.0 のテストでは expo-file-system を「ファイルの有無だけを集合で持つ偽物」（`test/fakeFileSystem.ts`）に差し替えていたが、フォルダの移動・名前変更・更新日時・一覧を扱えず、v2.0 の処理を確かめられない。

## 決定
- アプリのコードは expo-file-system の `File` / `Directory` を直接使う（ファイル操作のための独自の抽象型は作らない）
- テストでは jest の `moduleNameMapper` で expo-file-system を `test/nodeFileSystem.ts` に差し替える。これは使う範囲の API（`list` `info` `move` `rename` `create` `delete` `write` `text` `exists` `size` `modificationTime` `copy` など）を、テストごとの一時フォルダ上で node の `fs` を使って実装したもの
- 外部変更のテストは、node の `fs` で一時フォルダの中身を直接書き換えて起こす

## 検討した選択肢
- **アプリ側に `FileSystem` 型を作り、expo 実装と node 実装を差し替える** — ADR 0008 の `Db` と同じ形で筋は通るが、アプリのコードが expo-file-system の API と独自の型の両方を知ることになる。差し替えはテストのためだけなので、モジュールの置き換えで足りる（詳細設計書 3.3: 抽象化は今2つの実装が必要な場合だけ。ここでの2つ目はテスト側に閉じている）
- **メモリ上の偽物を作り込む** — フォルダの移動・更新日時の振る舞いを自前で再現することになり、本物とずれるおそれがある。node の fs なら APFS に近い振る舞いがそのまま得られる

## 結果
- services・外部変更の反映を、実際のファイル操作でテストできる
- 偽物の API は expo-file-system の実際の振る舞い（存在する移動先への `move` が失敗するか、など）に合わせる必要がある。合わせ方に迷うものは、シミュレータで本物の振る舞いを確かめてから偽物に反映する
- 既存の `test/fakeFileSystem.ts` は置き換える
