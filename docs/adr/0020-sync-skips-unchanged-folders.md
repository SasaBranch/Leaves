# 0020. 走査はフォルダの更新日時で中身の確認を省き、アプリ自身の変更では記録を更新しない

- 状態: 承認
- 日付: 2026-09-28

## 背景
外部変更の反映（基本設計書 6.7）は、起動時と前面復帰時に本棚フォルダ全体を走査する。ノート1,000件・ページ5,000枚でも、変更がなければ 5秒以内に終える必要がある（NFR-P-07）。ADR 0015 で、expo-file-system の `Directory.list()` は 5,000件の一覧に約2秒かかることが分かっている。

macOS（APFS）で、フォルダの更新日時は中のファイル・フォルダの追加・削除・名前変更で変わり、ファイルの内容の上書きでは変わらないことを確認した（基本設計書 R-6）。

## 決定
- ノートブック・ノートごとに、前回の走査時のフォルダの更新日時を DB（`scanned_modified_at`）に持つ
- 走査では、更新日時が同じノートは `.leaves.json` も画像の一覧も読まない。更新日時が同じノートブックは直下の一覧を取らず、DB の子から作る（子はたどる）
- **アプリ自身の変更（ノート作成・名前変更・OCR 結果の保存など）では `scanned_modified_at` を更新しない**。アプリが変更したフォルダは次の走査で読み直されるが、フォルダが正本なので結果は同じになる

## 検討した選択肢
- **毎回すべてを読む** — ノート1,000件で `.leaves.json` 1,000個と画像一覧の読み込みになり、5秒に収まる見込みが低い
- **アプリ自身の変更のたびに、影響するフォルダの更新日時を記録し直す** — 変更の種類ごとに「どのフォルダの日時が変わるか」（親・移動元・移動先・OCR での `.leaves.json` の書き換え…）を正しく列挙する必要があり、漏れると外部変更を見落とす。見落としは誤り、読み直しは遅いだけなので、安全な側に倒す
- **ファイルの内容の変更も検出する**（画像ファイルの更新日時を毎回見る） — 全ページのファイル情報を読むことになる。内容の上書きは Finder での通常の操作では起きにくい（置き換えは削除＋追加になる）

## 結果
- 変更がなければ、走査はノートブック・ノートのフォルダの更新日時を読むだけになる（件数はフォルダの数）。実際の時間は事前検証 R-7 で計測する
- アプリで変更した直後の走査は、変更したノートの分だけ少し遅くなる
- 画像ファイルの内容だけを外部で上書きした場合は反映されない（OCR 結果が古いまま残る）。必要になったら、ノート表示から OCR を再実行できるようにすることで対応する
