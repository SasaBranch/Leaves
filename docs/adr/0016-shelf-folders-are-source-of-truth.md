# 0016. 本棚のフォルダを正本とし、SQLite は索引・キャッシュにする

- 状態: 承認
- 日付: 2026-09-28

## 背景
要件定義書 v1.2 で、本棚（Obsidian の Vault に相当）を追加し、本棚・ノートブック・ノートをフォルダとして保存して「ファイル」アプリ・Finder から操作できるようにすることになった（FR-X-01〜09）。外部でのフォルダの作成・名前変更・移動・削除や画像の追加も、アプリに反映する（Q-7: 完全に反映する）。

v1.0 は SQLite を正本とし、画像は `pages/{pageId}.jpg` に平らに置いていた。この形のままでは、外部から見ても何のノートか分からず、外部での変更を反映する手がかりもない。

## 決定
- **本棚フォルダの中身（フォルダ構造・画像・管理用 JSON `.leaves.json`）を正本** とする。フォルダ名＝ノートブック名・ノート名、ノートのフォルダ内の画像のファイル名順＝ページ順
- SQLite は本棚ごとの **索引・キャッシュ** とし、一覧・検索・ページ数などの集計を速くするためだけに持つ。失われても本棚フォルダから作り直せる
- ID・表紙色・OCR 結果など、フォルダ名で表せない情報は各フォルダの `.leaves.json` に持つ
- アプリでの変更は「本棚フォルダを変更 → DB に反映」の順。外部変更は起動時・前面復帰時の走査で DB に反映する
- v1.0 の整合性チェック（ADR 0015）は、この走査に置き換える

## 検討した選択肢
- **DB を正本のまま、フォルダは書き出し用の写し** — 外部での変更を反映するには結局フォルダと DB の突き合わせが必要で、どちらが正しいかの規則が複雑になる
- **1つの DB に本棚の列を足す** — フォルダ単位で本棚を独立させる要件（Q-6）に合わない
- **OCR 結果は DB だけに持つ** — DB が失われると全ページの OCR をやり直すことになる（NFR-R-05 を満たせない）

## 結果
- Finder で見たときにそのまま読める構造になり、外部変更の反映も「走査して DB を合わせる」1つの仕組みで済む
- DB への登録前にアプリが終了しても、次回の走査で追いつくため、保存処理の不整合の心配が減る
- 名前にファイル名の制約（使えない文字、同じ場所で一意）がかかる（基本設計書 5.5）。ノート名の初期値も `:` を使わない形に変わる
- 外部変更の走査が性能上の課題になる（ADR 0015 で `Directory.list()` の遅さが分かっている）。フォルダの更新日時が変わっていないノートは中身の確認を省く（基本設計書 6.7、リスク R-7）
