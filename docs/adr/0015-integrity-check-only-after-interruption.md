# 0015. 画像フォルダの整合性チェックは、前回の画像操作が途中で終わったときだけ行う

- 状態: 承認
- 日付: 2026-09-28

## 背景
基本設計書 6.5・詳細設計書 9.6 では、起動のたびに `pages/` `thumbs/` のファイル一覧を取り、DB にない画像（保存・削除の途中で終了したときの残骸）を消すことにしていた。

性能計測（#33）でノート1,000件・ページ5,000枚のテストデータを入れたところ、expo-file-system の `Directory.list()` が5,000件で約1.7〜2.5秒かかり、しかも JS スレッドを止めるため、起動直後のライブラリの表示が約2.6秒待たされた（通常は十数ms）。実データではページ画像とサムネイルで倍の件数になる。NFR-P-01（起動2秒以内）・NFR-P-02 を満たせない。

## 決定
- 画像ファイルと DB の両方を書き換える操作（ノート作成・ページ追加・ノート／ページ／ノートブックの削除）を `withImageOperation` で囲み、実行中は `Documents/image-operation-in-progress` という印のファイルを置く。操作が終わったら（失敗しても）消す。同時に複数の操作が走る場合は、最後の操作が終わるまで消さない
- 起動時は、印が残っているとき（＝前回が途中で終わった）だけ整合性チェックを行い、終わったら印を消す

## 検討した選択肢
- 毎回チェックする（従来どおり） — 数千枚で起動が数秒止まる
- `Directory.listAsRecords()`（軽い一覧）を使う — 内部用で将来削除予定と明記されている
- 数日に1回だけチェックする — その日の起動が数秒止まることに変わりはない
- ネイティブ側で別スレッドで一覧を取る — ネイティブモジュールの自作が必要で、問題の大きさに見合わない

## 結果
- テストデータ入りで、起動直後のライブラリ表示が約2,600ms → 約14ms になった（iOS 27 シミュレータ）
- 画像を1枚書いてから DB に登録するまで、または DB から消してから画像を消すまでの間に強制終了された場合だけ、次回起動が一度だけ遅くなる
- 印のファイル自体の書き込み・削除が失敗した場合は、残骸が消えずに残る（容量を少し使うだけで、利用者の見えるデータには影響しない）
