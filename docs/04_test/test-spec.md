## 1. 目的・範囲

### 1.1 目的
要件定義書 11章の受け入れ基準「テスト仕様書の項目がすべて合格している」を判定するため、実機・シミュレータ・エミュレータで行う **手動テストの項目・手順・期待結果** を定める。

### 1.2 範囲

| 対象 | 方法 | 本書での扱い |
|---|---|---|
| データ層・サービス層・純粋な関数 | Jest による自動テスト（122件以上。DB 制約、索引同期、並べ替え、OCR 状態遷移、PDF 座標計算、ファイル名変換など） | **再掲しない**。`npm run check`（型チェック・lint・テスト）がすべて成功することを前提条件とする（詳細設計書 12章） |
| 画面操作・ネイティブ連携（スキャナ、OCR、写真、共有シート、外観） | 手動 | 4章 機能テスト |
| 性能・信頼性・オフライン・使いやすさ | 手動（計測含む） | 5章 非機能テスト |
| 利用シーン S-1〜S-6 | 手動 | 6章 シナリオテスト |
| 保守性（NFR-M-01〜05） | `npm run check`、コードレビュー | 5.6 で確認方法のみ示す |

### 1.3 記入ルール
- 結果欄には `○`（合格）/ `×`（不合格）/ `−`（対象外。理由を備考に書く）を記入する
- `×` の場合は 8章の手順で Issue を起票し、備考に Issue 番号を書く
- UI 表示は「ノートブック」（内部名: フォルダ）、「ライブラリ」（内部名: ルート）で記載する（基本設計書 1.3）

## 2. テスト環境

| 区分 | 端末 | OS | 用途 |
|---|---|---|---|
| iOS 実機 | iPhone 15 | iOS 26.6.1 | 全項目（スキャン・カメラ権限・性能計測を含む） |
| iOS シミュレータ | Xcode 27 付属シミュレータ | iOS 27 | 画面・データ系、外観の切り替え（ADR 0012 / 0014 の確認）。カメラを使う項目は `−` |
| Android エミュレータ | Google Play 入りイメージ（Pixel 系） | Android 10（API 29）以上。最低版の確認に API 29 を1回使う | 全項目。スキャナ（ML Kit Document Scanner）・OCR（ML Kit）は Google Play 開発者サービスが必要（NFR-E-04） |

- ビルド: 開発ビルド（`npx expo run:ios` / `npx expo run:android`、要件 C-2）。性能計測は Release 構成（`--configuration Release` / `--variant release`）でも行う
- OCR エンジンは OS で異なる（iOS: Apple Vision、Android: ML Kit。ADR 0013）。OCR 関連の項目は両 OS の結果を比べて記録する
- エミュレータのカメラは仮想シーンのため、スキャン品質（輪郭検出・台形補正）の判定は実機でのみ有効とする

> **未決**: 要件 11章は「iOS 実機・Android 実機の双方で動作する」ことを求めているが、**Android 実機は用意できていない**。Android はエミュレータでの結果で代替してよいか、実機を調達するかは **受け入れ判断としてユーザーと相談する**。代替する場合、スキャン品質（T-S-02・T-S-03）と性能（NFR-P）の Android 結果は「参考値」として扱う。

## 3. テストデータ

| 名称 | 内容 | 作り方 | 主な用途 |
|---|---|---|---|
| 大量データ | ノートブック「テストデータ」配下にノート 1,000件・ページ 5,000枚（OCR テキスト入り） | 開発ビルド限定の「テストデータ生成」操作（#32、`__DEV__` のときだけ表示）を実行 | NFR-P-01〜03、検索、一覧スクロール |
| 印字ノート | 印刷された日本語の書類・プリント（英数字混在を含む）3ページ | 実機でスキャン | OCR 精度、PDF 透明テキスト、検索 |
| 手書きノート | 手書きの日本語ノート 3ページ（数式・英単語を含む） | 実機でスキャン | OCR（手書き、要件 P-3）、シナリオ |
| 複数ページ | 10ページのノート（ページ番号を大きく書いた紙） | 実機でスキャン、または写真から取り込み | スワイプ、並べ替え、ページ削除、中断テスト |
| 階層 | 「大学 / 線形代数 / 演習」「趣味」のノートブック | 手動作成 | フォルダ系、移動、範囲検索 |
| 写真 | 書類を撮影した写真 5枚、文字のない風景写真 1枚 | 事前に写真アプリへ保存（エミュレータはドラッグ＆ドロップで追加） | 取り込み、OCR 失敗・空テキスト |

- 大量データはテスト終了後、ノートブック「テストデータ」を削除して片付ける（削除自体も T-F-13 の大量版として確認する）
- ファイル名変換を確認するため、タイトル「議事録: 10/15」のノートを1件用意する

|---|---|---|
| 1 | Must の機能要件がすべて実装され、iOS 実機・Android 実機で動作する | 4章のうち要件ID が Must の項目が、両 OS ですべて `○`。`−` は理由（再現困難・環境制約）が備考にあり、代替の確認（単体テスト等）が済んでいること |
| 2 | 利用シーン S-1〜S-6 を実機で一通り実行できる | 6章 T-SN-01〜06 が両 OS ですべて `○` |
| 3 | 性能目標（NFR-P）をテストデータ（ノート1,000件・ページ5,000枚）で満たす | 5.1 の T-P-01〜04 が iPhone 15 で目標値以内。T-P-05・06 は目安のため、超過した場合は値を記録してユーザーと相談 |
| 4 | テスト仕様書の項目がすべて合格している | 本書の全項目が `○` または理由付きの `−`。Should 要件（FR-F-08、FR-Q-05、FR-E-04）の `×` は、Issue を起票し MVP 後の対応とすることにユーザーが同意した場合に限り許容 |

- 前提条件: `npm run check` が成功していること（1.2）
- 不合格（`×`）の項目は、修正後に **その項目と関連するシナリオ（6章）を再テスト** する
- Android 実機がない場合の扱いは 2章の未決事項に従う

## 8. 不具合の記録方法

不具合は GitHub Issue（SasaBranch/Leaves）に起票し、マイルストーン **「M6 デバッグ」** を付ける。本書の結果欄に `×` と Issue 番号を書く。

### 8.1 Issue テンプレート

```markdown
## 概要
（1行で。例: 1ページだけのノートでページを削除すると確認が出ない）

## テスト項目
T-N-11（要件 FR-N-08）

## 再現手順
1.
2.
3.

## 期待する結果
（本書の期待結果を引用）

## 実際の結果

## 端末・環境
- 端末 / OS: iPhone 15 / iOS 26.6.1
- ビルド: Debug / Release、コミット: <hash>
- 再現頻度: 毎回 / ときどき（N回中M回）

## スクリーンショット・ログ
（画面収録、開発ビルドのコンソール出力）
```

### 8.2 起票ルール

| 項目 | ルール |
|---|---|
| タイトル | `[T-xx-nn] 現象の要約`（例: `[T-S-10] 保存画面を閉じるときに破棄確認が出ない`） |
| ラベル | `bug`。OS 固有なら `ios` / `android` |
| 重要度 | データ消失・起動不可・Must 要件の未達は優先。見た目のみの不具合は後回し可 |
| 仕様との差 | 実装と設計書の差（T-S-10、T-E-09 など）は、設計を直すか実装を直すかを Issue 上で決め、結論を設計書または本書に反映する |
